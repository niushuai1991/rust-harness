- 状态：设计草稿；命令 Hook 和项目、插件准入有阶段性实现，完整能力尚未实现或验收。

## 目标与范围

支持通过用户、项目和插件配置注册常用 Agent 生命周期及工具事件的命令处理器。首期范围为下列九种事件；具体配置格式、失败语义与兼容范围仍需在实施设计中细化，不宣称兼容其他产品的全部配置或事件。

## 首期事件

| 事件 | 触发时机 | 用途及作用边界 |
|---|---|---|
| `SessionStart` | 会话开始或恢复后，处理首条消息之前 | 注入项目约定或环境提示；输入应标识启动来源，避免把恢复误当成新建。压缩后触发方式仍需细化。 |
| `UserPromptSubmit` | 用户消息进入模型上下文之前；运行中插话在实际纳入上下文的边界处理 | 检查输入或补充上下文；输入应区分普通消息和插话，不改变插话既有的顺序与结算约定。 |
| `PreToolUse` | 工具原始参数校验通过后、权限检查之前 | 可拒绝、要求审批、改写工具参数或补充上下文；改写后须重新校验并执行现有权限检查。 |
| `PermissionRequest` | 工具调用需要发起权限审批时 | 提供审批相关信息或拒绝建议；首期不允许 Hook 自动批准或放宽权限策略。 |
| `PostToolUse` | 工具实际执行成功后 | 按工具调用提供后续处理或上下文；工具已经执行，不能将 Hook 结果描述为撤销操作。 |
| `PostToolUseFailure` | 工具实际执行失败后 | 提供失败诊断；在执行前因参数校验、Hook 或权限被拒绝的调用不视为工具执行失败。取消、超时及结果未知须单独标识。 |
| `Stop` | 模型准备正常结束当前回合时 | 可反馈未完成事项并要求继续；须提供防循环状态并限制连续继续次数。用户取消、预算耗尽和运行错误不能被 Hook 强制继续。 |
| `Notification` | Agent 需要用户处理时，如等待审批或 `ask_user` 答复 | 用于提醒；仅在实际进入等待时触发，无人在场而立即结算时不伪造等待。Hook 不能代替用户答复或批准。 |
| `PostToolBatch` | 一次模型响应中的工具批次全部结算后、下一次模型请求之前 | 按模型声明顺序汇总每次调用及结算状态并补充上下文；与每次调用各自的后置事件区分，批次只触发一次。 |

每个工具调用须按执行状态产生对应结算；后置事件与 `PostToolBatch` 不能改变既有调用结果或导致重复执行。取消或预算耗尽时不得为了触发批次 Hook 发起新的模型请求；异常终止时批次 Hook 是否执行及其输入需在实施设计中明确。

首期不包含 `PreCompact`、`PostCompact`、`SubagentStart`、`SubagentStop`、`StopFailure` 或 `SessionEnd`。会话启动和运行中插话的具体去重、崩溃恢复语义仍需细化，不得在历史回放时重放有副作用的 Hook。

## 配置来源

参考 [Claude Code Hook 配置位置](https://code.claude.com/docs/en/hooks#hook-locations)，使用设置文件中的 `hooks` 字段声明 Hook：

| 来源 | 路径 | 作用范围 |
|---|---|---|
| 用户设置 | `<数据目录>/settings.json`，默认 `~/.RustHarness/settings.json` | 使用该数据目录的会话 |
| 项目共享设置 | `<项目根>/.rh/.settings.json` | 当前项目，可由团队共享 |
| 项目本地设置 | `<项目根>/.rh/.settings-local.json` | 当前项目的本地设置，是否纳入版本控制由项目决定 |
| 插件 | `<插件根>/hooks/hooks.json` | 对应插件启用时 |

用户设置跟随现有数据目录解析规则：显式参数优先，其次 `RUST_HARNESS_DATA_DIR`，最后默认目录。无项目会话没有项目配置来源。项目源目录与副本、worktree 执行根之间的发现和信任身份映射需在实施设计中明确；不能因切换执行根绕过信任。

配置按来源保留，便于诊断和识别执行权限。下文给出合并顺序、重复声明、会话快照和局部禁用的建议；全局禁用规则及会话重新加载交互还需细化。项目内的可执行配置必须在通过明确的信任准入后才可执行；插件配置遵循插件启用及授权规则。设置文件中的其他字段不得因读写 Hook 配置被清除。

本节将 Claude Code、zcode、codex 和本项目现有规则中的可用方案落为实施建议；仍为设计草稿，不能将其全部视为已经实现。涉及 Claude Code 的格式参考其 [Hooks 参考](https://code.claude.com/docs/en/hooks#configuration)和[插件配置参考](https://code.claude.com/docs/en/plugins/manifest-reference#hooks)。

### 当前阶段及后续工作

- 用户、项目及授权插件的配置已接入九类事件的部分同步命令处理路径；事件和输出字段只实现了子集，不承诺完整 Claude Code 兼容。现有实现每次事件读取配置，尚未实现会话配置快照；工具 matcher 只支持精确名称列表，尚不支持正则；`onFailure` 和异步处理尚未实现。
- 项目配置按实际执行根逐条审核；桌面交互任务在开始或主要执行边界遇到未信任配置时暂停并提示审核，全部信任后继续，取消审核会取消任务；无人值守入口返回 `HOOK_TRUST_REQUIRED`。运行中其他竞争边界若配置变化，可能以待审核错误结束，需重新审核后继续。直接模式、副本及 worktree 使用各自执行根身份，不自动继承信任。
- 桌面设置的“项目 Hook 审核”提供查看、信任和撤销入口；命令行使用 `harness hooks review --session <会话ID>` 查看摘要，再用 `harness hooks trust --session <会话ID> --digest <摘要>` 信任，或用 `harness hooks revoke --session <会话ID> --digest <摘要>` 撤销。摘要覆盖声明和可识别的入口脚本，无法保证间接依赖和网络内容。
- 插件的 `hooks/hooks.json` 需要清单声明 `hooks.command`，安装时显式授予同名权限并启用插件；派发前检查工作区策略、授权、启用状态及安装包内容摘要。`${RH_PLUGIN_ROOT}` 在命令和参数中替换为插件版本目录。
- 已实现：所有来源的命令及参数中的 `${RH_PROJECT_DIR}` 与 `${CLAUDE_PROJECT_DIR}` 在执行前展开为当前工作区（hook 执行根，worktree 模式下即 worktree 路径），并以同名环境变量注入 hook 子进程。两个变量同值；`CLAUDE_PROJECT_DIR` 是为兼容 Claude Code hook 脚本而设的别名，目的是这类脚本不经修改即可在本项目运行（脚本内 `$CLAUDE_PROJECT_DIR` 依赖环境变量注入）。变量是运行时值，不参与信任摘要；含变量的命令暂不做入口脚本内容绑定，按声明级信任处理，派发前仍复核声明摘要。
- 会话快照、本文其他验收事项及所有竞争边界的交互恢复仍需完善，当前 Hook 不应作为完整安全策略。

### 配置示例

用户及项目 `settings.json` 使用同样的事件、匹配组、处理器三级结构。例如下列示例匹配本项目的 `shell` 工具，直接启动 PowerShell 可执行文件并将参数作为数组传入；路径仅作示范：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "shell",
        "hooks": [
          {
            "type": "command",
            "command": "powershell.exe",
            "args": ["-NoProfile", "-File", "C:\\Hooks\\check-shell.ps1"],
            "timeout": 30
          }
        ]
      }
    ]
  }
}
```

插件的 `hooks/hooks.json` 同样以顶层 `hooks` 包裹事件表；以下脚本路径通过插件根变量解析，具体变量名是本项目的设计，不是 Claude Code 的变量：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "write|edit",
        "hooks": [
          {
            "type": "command",
            "command": "powershell.exe",
            "args": ["-NoProfile", "-File", "${RH_PLUGIN_ROOT}\\scripts\\after-edit.ps1"]
          }
        ]
      }
    ]
  }
}
```

插件根目录的 `plugin.toml` 须声明 `permissions = ["hooks.command"]`。导入插件时还须在授权列表中显式填写 `hooks.command`，再启用插件；单独授予 WASM 的 `hooks` 权限不会授权本地命令。

这两个示例借鉴 Claude Code 的配置形状，而非声称脚本、工具名或所有字段完全兼容。首期只声明同步 `command` 处理器：无 `args` 时按所指定的 shell 执行 `command`；有 `args` 时直接启动可执行文件，不经 shell。项目目录变量的展开与注入已有实现及测试契约（见「当前阶段及后续工作」）；Windows shell 的选择、默认值与其余转义规则仍需形成明确的实现及测试契约。HTTP、MCP、prompt、agent 和后台异步处理器暂不支持，遇到不支持的类型或字段须诊断，不能悄悄执行成其他含义。

### 来源合并、匹配与更新

- 建议按用户、项目共享、项目本地、已启用插件的顺序合并；来源内按配置顺序执行，插件之间按稳定的插件标识排序。相同声明不自动去重，分别记录来源。禁止以单一来源的局部禁用意外关闭其他来源；全局停用的作用范围另行明确定义。
- 建议沿用 zcode 的每会话配置快照，修改只保证新会话生效；信任撤销、插件禁用及脚本内容变化必须在每次实际派发前重新校验，不能因旧快照继续获得执行权。快照产生的确切时间、已存在会话如何重新加载，需与桌面草稿会话及恢复流程一同验收。
- `matcher` 参考 Claude Code：空值、缺省或 `*` 匹配全部；简单名称列表按精确名称匹配，其他模式按文档规定的正则规则处理，非法模式报诊断并跳过该匹配组。工具事件匹配本项目实际工具名，`SessionStart` 匹配来源，`Notification` 匹配通知类型；无匹配对象的事件不凭空套用工具名。是否引入 Claude 工具别名必须明确列出，不能默认视为完全兼容。
- 脚本标准输入为单个 JSON 对象及换行；输出通过 stdout、stderr 和退出码结算。公共字段参考 `session_id`、`cwd`、`permission_mode`、`hook_event_name`，工具事件另提供 `tool_name`、`tool_input` 和 `tool_use_id`。事件专用字段参考 Claude 文档并按实际可用性定义；本项目使用 SQLite 事件，不应伪造 Claude JSONL 路径或声称支持其完整 transcript。

### 项目信任和插件授权

- **已确认：项目 Hook 未通过审核时暂停任务并提示审核，不跳过后继续。** 审核需展示配置来源、事件、命令及可识别的入口脚本；拒绝或取消审核不能视为信任。在无法交互的 CLI、ACP、自动化及无人值守场景返回清晰的待审核错误，不能无期限等待或自动放行。
- 参考 zcode，以项目身份和 Hook 声明内容摘要建立可撤销的逐条信任；可识别的直接入口脚本路径及内容也进入摘要。修改声明或该脚本后须重新审核，实际派发前复核，以减少审核和执行之间的变化。对无法识别的脚本、脚本继续加载的依赖及网络内容，必须明确提示无法由摘要完整覆盖，不能声称已验证完整依赖链。
- 项目配置从会话实际执行根发现；宿主管理的 worktree 仅在能证明与源项目的关联且声明及入口内容一致时继承信任。普通 worktree、副本和路径重定向的身份、符号链接处理、审核展示内容及派发前复核须有明确实现与测试，不能仅凭路径字符串或调用方自报身份放行。
- 现有插件以 WASM 权限交集执行，`hooks` 授权不自动代表执行本地命令的授权。插件命令 Hook 应有单独声明与显式授权，并受工作区策略及执行位置约束；插件禁用、权限撤销、升级或替换后必须重新核对。插件安装包的不可变版本与路径校验沿用现有机制，不能绕开原有插件的隔离和授权。
- 需提供桌面审核入口和适用于 CLI 的查看、信任、撤销入口；无人在场时只报告待审核状态，不代替用户决策。信任决定发生在副作用执行之前，恢复后不能重放已完成的 Hook。

### 事件决策与失败

| 事件 | 可影响当前流程的建议结果 | 默认失败处理建议 |
|---|---|---|
| `SessionStart` | 添加上下文；按来源区分新建、恢复和压缩 | 记录诊断，正常继续 |
| `UserPromptSubmit` | 添加上下文或拒绝当前输入 | 记录诊断；插话被拒绝时按现有规则结算为未处理并保留用户内容 |
| `PreToolUse` | 拒绝、要求审批、改写参数或添加上下文；改写后重新校验并审批 | 默认报告失败并继续；允许配置失败即阻断，不能把运行失败当作明确允许 |
| `PermissionRequest` | 提供理由或拒绝；不得自动批准 | 记录诊断并按现有审批流程处理 |
| `PostToolUse` / `PostToolUseFailure` | 添加与该次调用关联的上下文；不能撤销工具结果 | 记录诊断，保留原工具结果 |
| `Stop` | 提供反馈并请求继续；连续继续上限建议参考 zcode 的 3 次 | 记录诊断并结束正常回合；不得以 Hook 失败阻止用户取消或绕过预算 |
| `Notification` | 发出提醒，不能代替审批或答复 | 记录诊断，不改变等待与审批 |
| `PostToolBatch` | 按声明顺序汇总结果并注入一次上下文 | 记录诊断，不更改已结算的工具结果 |

建议参考 Claude Code 的 JSON `hookSpecificOutput`、`additionalContext`、`permissionDecision` 和 `updatedInput` 字段；退出码 `0` 表示成功，`2` 的效果由事件分别规定，其余失败按该事件及处理器的失败策略处理。不能将 `PermissionRequest` 的退出码 `2` 直接解释为 Claude 的拒绝决定：其结构化拒绝和本项目不允许自动批准的限制须单独实现。字段白名单、未知字段、相互冲突输出、stderr 上限及精确投影规则须在实施前细化。

同一事件有多个 Hook 时，拒绝不能被其他 Hook 的放行覆盖；参数改写的处理顺序、多个改写的冲突及在拒绝后是否继续执行其余 Hook 必须固定并测试。Claude Code 的处理器均执行后合并结果；本项目的顺序、副作用与取消策略应明确列为适配选择，不以此声称完全兼容。

建议在 `PreToolUse` 中将 `ask` 定义为更严格的决策：在允许交互的模式下强制进入用户审批，不因 `auto` 或 `guarded` 自动放行；`never` 保持拒绝，无人在场无法审批时拒绝。其他 Hook 的 `allow` 只能表示本 Hook 不阻止，不能覆盖其他 Hook 的拒绝、已有审批或计划模式限制。只有最终需要实际询问用户的调用才产生 `PermissionRequest` 和等待型 `Notification`；自动批准或自动拒绝的记录不能伪装成用户等待。

建议命令处理器提供 `onFailure: "continue" | "block"`：默认 `continue` 表示记录错误后由原流程继续，而非记录为明确同意；`block` 仅对仍可阻止的前置动作生效。`PermissionRequest` 不能通过失败或 `allow` 获得自动批准；`Stop` 失败不能无限要求继续；执行后的事件不能撤销已完成的副作用。用户取消始终优先于失败策略。字段和默认值以最终规范为准。

### 执行、展示与验收

- 受限模式扩展现有 Windows 进程接口，提供 JSON stdin、退出码、受限令牌、Job Object 进程树清理和有界 stdout/stderr；无法建立沙箱时拒绝启动。直接模式以宿主权限执行的差异须在审核时明确显示，不能把 Hook 放行当作工具审批。用户级和插件级脚本位于执行根之外时，需验证受限令牌对脚本的只读访问方式，不能为此放宽整个数据目录的写权限。
- 单次 Hook 默认超时与输出大小建议参考 zcode（60 秒、32 KiB），允许合理配置并设置硬上限；取消与超时终止整棵进程树。执行失败、拒绝和跳过都记录可关联会话、事件、来源、调用 ID、时长与状态的持久事件；命令、参数和输出可能含敏感内容，默认不将命令原文写入模型上下文。
- `PostToolUse` 可能运行格式化等写操作。工具批次的 prepare、执行与结算仍遵守现有串行屏障及声明顺序；不能因为原工具只读就推断命中的 Hook 可并发。`PostToolBatch` 在所有已接收调用有结果或明确未知状态后触发；取消、预算耗尽和崩溃恢复不得靠 Hook 重新执行工具。
- 参考 Claude 的 `/hooks` 只读展示与本项目 Skills 管理方式：CLI 与桌面应至少能查看来源、匹配、有效状态、信任、最近运行结果和错误；信任、撤销与配置编辑的具体交互另列设计。视图消费同一运行时状态，不能让 UI 独立决定是否执行。
- 验收包括九事件各自的匹配、触发、输入输出和成功/失败路径；配置合并与重载；信任变更、脚本替换与 worktree；权限五档和计划模式；有无项目、四端及无人值守；插话与工具并发、取消与恢复；输出限制、超时和 Windows 进程树清理。文档示例须经过真实配置加载测试。

- [Claude Code Hooks 参考](https://code.claude.com/docs/en/hooks)提供事件、配置、匹配及输入输出语义；本设计根据项目权限与运行机制选择适用部分。
- zcode 的 `docs/hooks-runtime-contract.md` 定义七类事件、匹配、标准输入和运行结果；项目配置须经过内容与工作区绑定的信任准入。
- codex 的 `codex-rs/protocol/src/hooks.rs` 定义匹配组与命令处理器，另有模型、压缩和子代理等事件；`codex-rs/core/src/hook_runtime.rs` 负责运行结果与上下文整合。
- 本项目已有 WASM 插件 `before_request`、`before_tool` 和 `after_tool` 钩子；`prepare_call` 在改写后重新检查工具定义和参数，再计算审批，计划模式跳过插件钩子。

## 必须保持的边界

- 副本、worktree 和无项目 scratch 中，命令处理器必须使用对应执行根、受限令牌和 Job Object；直接模式执行规则须明确告知用户。超时与取消须清理整个进程树。
- 计划模式不能执行任意命令 Hook，也不能因为 Hook 放行而绕过审批、工具参数校验或计划模式白名单。
- 项目目录中的可执行配置未建立信任机制前不得自动执行；插件 Hook 不得绕过插件启用与权限控制。
- Hook 输入输出需要大小限制和超时；错误、退出状态与跳过原因须可观察，避免误将失败当作允许或成功。
- 工具输入改写后必须重新进行 schema 校验和审批；结果事件与模型上下文须保持可重建，不得在恢复历史时重放副作用。
- 并发工具批次的前后事件要保证每次调用与结果对应；拒绝、实际执行失败、取消及超时须明确区分。

## 实现前需解决

现有 `ShellService::run_in` 返回退出码并清理进程树，但标准输入固定为空；`spawn_stdio_in` 支持读写标准流，但公开接口没有提供退出状态。命令 Hook 同时需要标准输入、受限执行、可靠退出码、有界输出和取消清理，需扩展平台层并针对 Windows 集成测试，再接入运行时。各事件的输入输出格式、匹配、冲突及失败处理，`SessionStart` 的首次触发和会话恢复，`Stop` 的阻止完成及重复触发保护，以及 `Notification` 和 `PostToolBatch` 的并发和取消边界也需要定义并测试。
