# Agent 执行性能优化规范

- 日期：2026-11-15（设计草案）
- 状态：待评审；本文只定义候选设计与验收要求，不代表已实现或性能收益已验证。
- 范围：单次模型步骤内的工具调度、流式工具执行、模型上下文管理、模型 HTTP 连接复用，以及衡量这些改动的基准。

## 背景与目标

本地体验中，使用 GLM-5.3-Flash 执行开发任务时，Rust Harness 有时比 ZCode 耗时更长。两边未使用完全相同任务及配置进行受控对照，现有数据不能证明具体根因或预期收益。本规范整理已确认的实现差异和安全约束，供后续测量、设计确认与实施；不假定任一优化能消除全部差距。

现有 Runtime 在完整模型响应后逐个执行工具，参见 `crates/harness-runtime/src/agent.rs`；模型投影从历史事件构造，支持手动 `/compact`；`HttpModel` 每次调用构建 HTTP 客户端。ZCode 当前源码包含安全分组、只读工具流中执行和自动压缩；它的实现不是本项目权限或事件契约的替代依据。

目标是减少可避免的等待和长会话上下文开销，同时保持事件回放、模型协议、审批、工作区隔离及预算语义。比较时必须单独记录模型轮数和工具步骤：调度优化不应被当作对任务轨迹差异的解释。

## 方案与边界

| 方案 | 收益与代价 | 本草案选择 |
|---|---|---|
| 不改运行时，仅测量 | 风险小，可识别瓶颈，但不会直接减少等待 | 作为任何优化的基线和决策前提。 |
| 对所有工具直接并发、流中执行 | 有机会减少等待，但可能乱序写入、绕过审批或使失败后的执行状态不明 | 不采用。 |
| 对明确安全的只读工具分组，渐进引入流中执行、上下文管理和连接复用 | 可分别测量和回退；需要定义事件、预算和失败边界 | 作为候选方向，逐项验证后实施。 |

非目标：本 PR 不修改业务逻辑；不承诺固定加速比例；不更改模型、effort、权限策略或工作区隔离；不把 ZCode 视为同任务对照；不实现桌面时间线优化。

## 一、工具调度

1. 在一次模型响应的工具批次内，按显式能力声明选择可并发的工具。只有已证明只读、无外部副作用、无交互、并发安全且不依赖其他调用结果的工具才能同组；未知能力、插件、MCP、自定义工具、Shell 和涉及写入或审批的调用默认串行。不能仅凭工具名称推断安全性。对并发成员的允许列表和分类依据应在实施时逐项审计。
2. 维护模型声明顺序：并发组前后的串行调用形成屏障，不跨越屏障重排。组内结果允许实际完成顺序不同，但持久化和实时事件中的结果按声明顺序提交，以保证现有事件回放及模型投影一致。单工具失败按现有错误语义结算，不得丢失其他调用结果或导致重复执行。
3. 并发上限必须有界，并限制同一会话资源占用；默认值与配置形式经基准确定。审批、计划模式、取消、超时、插件钩子和 read-before-edit 检查仍由现有边界执行；不能通过批次并发绕过。涉及可变状态或读取快照的钩子若未声明并发安全，整个相关调用退回串行。
4. 同一 call ID 最多结算一次；每个已接收调用都能关联唯一结果或明确的中断状态。取消与超时后等待执行任务有界收敛；无法确认副作用的调用标记结果未知，不自动重试。会话事件必须满足现有持久化及恢复契约，旧事件与消费者继续可用。

## 二、流式工具执行

候选方案是在模型响应仍在接收时，仅对完整解析、参数校验通过且符合上一节安全条件的工具进行提前只读执行；流结束后确认工具批次、调用 ID 与结果，再以稳定顺序提交结果并进入下一次模型请求。部分参数、未知工具、需要审批、交互、可写或非并发安全的工具只能在完整响应结算后按既有路径处理。

- 提前执行不得触发插件副作用、修改工作区、对外写入、提权或暴露未经确认的结果。重复 ID、无效参数、协议错误、断流、取消和超时都不得让同一调用再次执行或留下无法解释的已提交结果；取消流中工作并隔离未确认结果，不能把它们当作完整模型响应回放。
- 必须可证明流中调用的声明顺序，且它与所有更早但尚未完成的调用均可安全并行，才可提前执行；前面存在写入、未知能力或其他串行屏障时必须等待屏障完成。若协议无法可靠证明顺序，则该批次退回流结束后调度，防止先声明的编辑被后声明的读取越过。
- [每回合 Token 预算](token-usage-budget.md)目前要求预算耗尽的响应中的工具“未执行”。流中提前读取发生在 usage 结算之前，与该要求存在冲突。因此本草案**不授权直接实现该行为**：实施前必须先明确并修订预算规范，定义是否允许无副作用的投机读取、如何记账与审计，以及超限/用量缺失时的事件语义；在修订获接受前保持现有执行时点。
- 协议适配必须明确“工具参数完整”的可靠信号；不能从部分 JSON 可解析推断调用已完成。缺少可靠完成信号的协议退回流结束后执行。比较应记录工具完成与模型流结束的重叠区间，而非只统计多工具批次。

## 三、上下文管理

- 候选方案是在每次主模型请求前检查当前模型的有效上下文窗口及输出预留，接近阈值时压缩模型投影，再继续原请求；手动压缩保留。阈值、预留策略、默认启用方式及配置由后续基准和产品设计确定，不把某个百分比当作已验证事实。
- 压缩只影响后续发送给模型的投影；原始 SQLite 事件、时间线、导出、搜索与审计不删除不改写，遵守[长会话时间线规范](long-session-timeline.md)。只在完整工具调用和结果配对的边界进行；摘要应保留用户目标、关键约束、未完成事项和必要的工作状态。压缩后的投影必须能正确恢复并供三个协议编码。
- 自动压缩本身的模型请求、耗时、usage、失败和取消应可观察，并计入当前回合共享 token 预算；不得通过压缩绕过预算限制。手动压缩维持现行独立请求的预算语义。自动与手动压缩必须与活动回合串行，基于固定历史边界生成摘要，并原子确认边界仍有效后再提交；期间不能丢失新消息或工具结果。失败、取消、无窗口元数据及摘要无效时，不替换现有有效投影、不无限重试；是否继续请求须结合剩余上下文容量给出明确且可诊断的结果，避免反复请求溢出。
- 可另行评估对旧工具输出做有界投影，但必须保留调用与结果配对及关键上下文，不能破坏附件引用和恢复；清理策略、触发条件、信息损失与回退需要独立验证，不能默认为当前已有能力。

## 四、模型 HTTP 连接复用

- 候选方案是在供应商传输层复用长生命周期的 `reqwest::Client` 及连接池，而不是每次模型调用新建；复用边界必须覆盖会影响传输的配置，例如代理、TLS、认证方式、默认请求头与重定向策略。密钥和会话专属头按请求注入，不得跨配置或账户泄漏。
- 供应商、代理、凭据或证书配置变化时，新请求使用新配置；已进行请求按原快照完成或取消。客户端生命周期与淘汰策略有界；连接失效时不得对可能已被服务端接受的模型请求盲目重试。
- 保持三协议编码、usage、取消、流空闲超时和错误语义。通过本地可控 HTTP 服务记录连接数、请求数和首字节时间，验证同配置可复用、不同配置隔离及变化后生效；真实网络的收益单独测量，不能将连接建立时间推算为任务总收益。

## 验证与决策

1. 先记录当前版本基线，再按单项开关对照：相同机器、项目快照、任务、模型、effort、供应商/协议、权限、上下文起点及网络环境；记录版本、样本数、任务完成质量、总耗时、模型请求与工具调用次数、输入/输出及缓存 token、模型首字节/完成时间、工具耗时、人工等待和错误。多次运行并报告分布，不以单次结果断言收益。
2. 使用可控假模型和工具分别验证：只读并发的实际重叠、串行屏障和结果顺序，包括编辑后读取同一文件、流中声明顺序不可证明，以及完成顺序倒置和中途崩溃后的事件回放；失败/取消/超时/重复 ID；权限、钩子与计划模式；三个协议的分块与异常流；预算耗尽及 usage 缺失；断流后的恢复和无重复执行。
3. 使用可复现长会话 fixture 验证窗口阈值、完整调用边界、摘要失败/取消/恢复、预算与原始历史不变，并测量压缩开销及后续请求收益。HTTP 测试验证连接复用及配置隔离。比较前后结果质量，性能提升不能以丢失约束或审计为代价。
4. 四项优化可独立启停或回退到既有行为；开关范围及默认值在实施设计确定。每项上线前记录基线和效果；无可测收益或改变安全语义时暂停该项，而不是承诺统一加速比例。
